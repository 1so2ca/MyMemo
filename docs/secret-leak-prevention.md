# 公開リポジトリの秘密情報漏洩防止

## 目的

認証情報をリポジトリへ混入させず、誤操作があっても commit と push の複数段階で停止する。単一の検出ツールを完全とはみなさず、保管・ファイル経路・内容・リモート受信・監査・権限の異なる層を組み合わせる。

## 標準構成

### 1. 秘密値をリポジトリ外へ置く

- 本番の秘密値はクラウドの Secret 機能へ保存する
- CI の秘密値は CI サービスの Secrets へ保存する
- CLI 認証は OAuth または OS の資格情報ストアを使う
- ローカル開発用の秘密値は `.env` や `.dev.vars` に置き、Git では追跡しない
- 設定ファイルとソースには、Secret の名前だけを書き、値を書かない

### 2. 秘密ファイルの追跡を拒否する

`.gitignore` に加え、Git hook で禁止ファイルを検査する。`.gitignore` は `git add -f` で回避できるため、それだけを防止策にしない。

標準の禁止対象:

- `.env`、`.env.*`
- `.dev.vars`、`.dev.vars.*`
- `.wrangler/`
- `*.pem`、`*.key`
- `*.p12`、`*.pfx`
- `*.jks`、`*.keystore`
- `id_rsa`、`id_ed25519`
- `credentials.json`
- `service-account*.json`

値を含まない `.env.example` と `.dev.vars.example` は許可できる。例外を増やす場合は、内容を確認して理由を残す。

### 3. Gitleaks で内容を検査する

Gitleaks のバージョンを固定し、出力では Secret をマスクする。

- pre-commit: ステージ済み差分を検査する
- pre-push: push 前に Git 履歴を検査する
- 初回公開前: Git 履歴と現在の作業ツリーを両方検査する
- Gitleaks が未導入または実行失敗の場合も、操作を許可せず fail-closed にする

実行例:

```sh
gitleaks git --pre-commit --redact --staged --verbose
gitleaks git --redact --verbose --log-opts="--all" .
gitleaks dir --redact --verbose .
```

### 4. リモート受信時にも拒否する

GitHub では Secret scanning と Push protection を有効にする。ローカル hook が未設定・故障・回避された場合の独立した防御になる。

無料の公開リポジトリでは主に既知プロバイダーのトークンが対象になる。一般的なパスワード、独自形式、古い形式まで保証されない。Generic patterns や Custom patterns は契約とリポジトリ種別によって利用できないため、利用可能と仮定しない。

### 5. CI は監査として使う

公開リポジトリの CI は push 後に動く。秘密が公開される前の防止策にはならないため、ローカル検査や Push protection の代替にしない。

CI でも全履歴を Gitleaks で再検査し、ローカル hook の回避、環境差、設定不備を検出する。外部 Action は可変タグではなく commit SHA へ固定し、最小権限で実行する。

### 6. 認証情報の影響範囲を限定する

- Global Key より、対象・操作・期限を限定した Token を使う
- デプロイ、データベース、外部 API、CI で認証情報を分離する
- CI の権限は必要最小限にする
- PoC や一時作業の終了時に不要な認証情報を失効する
- 長期共有せず、必要に応じて短期間でローテーションする

## Git hook の要件

- hook はリポジトリで版管理する
- `core.hooksPath` で版管理したディレクトリを指定する
- Windows でも動くよう、hook の改行コードを LF に固定する
- 禁止ファイル検査を先に行い、その後 Gitleaks を実行する
- `--no-verify` は通常運用で使用しない
- clone 後に hook が有効か確認する手順を用意する

## 公開前チェック

1. remote が意図した公開先か確認する
2. stage 対象をファイル単位で確認する
3. 禁止ファイルが現在と履歴のどちらにもないことを確認する
4. Gitleaks で履歴を検査する
5. Gitleaks で未追跡を含む作業ツリーを検査する
6. リモートの Push protection を確認する
7. push 後の CI が最小権限であることを確認する

高い保証が必要な場合は、非公開のステージングリポジトリで検査を完了し、合格した成果物だけを公開リポジトリへ反映する。ただし、リポジトリ同期と履歴管理の運用負荷が増える。

## 漏洩を検出した場合

1. commit と push を停止する
2. 対象の認証情報を先に失効・再発行する
3. 作業ツリーだけでなく Git 履歴からも削除する
4. 全履歴と作業ツリーを再検査する
5. 公開済みなら、短時間でも第三者が取得済みと仮定する
6. 発行元サービスの監査ログで不正利用を確認する

ファイルを削除するだけでは、過去の commit に秘密が残る。履歴を書き換えても、既に取得された秘密は無効にならないため、失効・再発行を最優先にする。

## 限界

- Gitleaks は未知の形式や通常の文字列に見える秘密を見逃す可能性がある
- Git hook は意図的に回避でき、clone ごとに有効化が必要
- Push protection はすべての秘密形式を対象にしない
- CI の検出は公開後になる
- どの対策も、既に取得された秘密を回収できない

漏洩を完全保証するのではなく、秘密を置かない設計、異なる層での拒否、最小権限、迅速な失効を組み合わせてリスクを下げる。
